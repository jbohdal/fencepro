## Known Critical Issues to Resolve

These two issues are confirmed broken right now and must be fully resolved as part of this pass. Diagnose them early in Phase 1, fix them in Phase 2, and verify them in Phase 5. Do not leave either of them in a partial state.

### Critical Issue 1: Address Autocomplete is Completely Broken on the New Customer Form

**Current behavior:** On the new customer form, the address field does not accept any input at all. You cannot even type into it. The field is unusable.

**Intended behavior:** As the user types into an address field, address suggestions should auto populate from a places API (most likely Google Places, since Google Maps is one of the integrated services). The user should be able to type freely, see suggestions, select one, and have the parsed address components populate the structured fields (street, city, state, postal code, country, latitude, longitude).

**Important context:** This pattern existed and worked elsewhere in this same codebase at some point. It is not a feature that needs to be designed from scratch. It needs to be located, understood, and restored.

**What to do:**

1. Search the entire codebase for any existing address autocomplete implementation. Look for references to Google Places, Places API, Autocomplete, useAutocomplete, address suggestions, place_id, address_components, or any wrapper component that handled address input. Check git history if available.
2. Identify the most recent or most polished working version. If more than one pattern exists, pick the cleanest one and standardize on it.
3. Diagnose why the new customer form version is broken. Likely culprits include: the Google Maps script not loading on that route, a stale or missing API key, a controlled input fighting the autocomplete library, an event handler that calls preventDefault on every keystroke, a CSS layer covering the input, or a dependency that was upgraded and broke the integration.
4. Fix the root cause, not the symptom. Make sure the user can type freely into the field and see suggestions appear.
5. Once fixed, apply the same address autocomplete pattern uniformly to every place in the app where a structured address is entered. This includes at minimum: new customer form, edit customer form, job site address, vendor address, billing address, shipping address, and any inventory location address. If you find additional places, fix those too.
6. Verify the parsed address components populate the structured database fields, not just a single freeform string. Latitude and longitude should be saved when available.

### Critical Issue 2: Modules Do Not Talk to Each Other

**Current behavior:** Entries made in one part of the app are not propagating to other parts of the app where that data should appear. Numbers that should populate automatically from upstream entries are missing, stale, or require manual reentry. Automations that should fire across modules are either not firing or not propagating their effects.

**Intended behavior:** EZ Biz is a connected system. Every value entered in one place should flow to every place that depends on it. The trigger automation engine should fire reliably across module boundaries. The agent must read the entire schema and the entire automation engine, build a complete map of how data is supposed to flow, and confirm every flow actually works.

**What to do:**

1. Read every Prisma model and document every relation. Build an internal graph of how the data is connected.
2. Read the trigger automation engine (rules, conditions, actions) and document every cross module effect it is supposed to produce.
3. For every module pairing, write down what data should propagate in each direction. Examples (not exhaustive):
   * Accepted quote line items should populate the pull sheet on the customer file with no manual reentry.
   * Quote totals should populate the customer balance and feed the AR module.
   * AR balances should feed the cash flow projection engine.
   * Scheduled jobs should appear on the unified Operations board and feed expected revenue into the cash flow projection.
   * Rain day flags should cascade to every downstream pending scheduled job.
   * Inventory consumption from a job should decrement stock based on the recipe / bill of materials.
   * Reorder points being crossed should automatically generate a purchase order.
   * Customer notes, billing data, and selected CRM data should appear in the customer portal through the selective adapter, never raw.
   * Trigger automations defined in the engine should fire on the events they declare and propagate their actions to every affected module.
4. Walk every flow in the live app. For each flow that does not work, diagnose the root cause and fix it. Common failure modes include: the upstream write happens but no event is emitted, the event is emitted but no subscriber is registered, the subscriber runs but updates the wrong record, the update happens but the frontend reads from a stale query, or the propagation works for create but not for update or delete.
5. Where propagation requires recalculation (cash flow projection, AR aging, inventory levels, projected schedule after rain), confirm the recalculation runs every time an upstream input changes, not only on a manual refresh.
6. Save the data flow map you built to `/DATA_FLOW_MAP.md` at the repo root so the human can review it.
